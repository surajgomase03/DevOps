## 1. What Is Amazon S3

### 1.1 Definition

1. **S3** stands for **Simple Storage Service**. It is AWS's **object storage** service.
2. You store data as **objects** inside **buckets**, and access them through an HTTPS API (Console, CLI, SDKs, REST) or through AWS services.
3. It is designed for very high **durability** (11 nines, see section 3), virtually unlimited capacity and pay-for-what-you-use pricing.
4. S3 is **not a file system** like `/home` or `/var`. There are no real folders, no file locking and no in-place partial edits. An object is written or replaced as a whole.

### 1.2 Why it is needed

1. **Durable storage** for backups, artifacts, logs and media without managing disks.
2. **Scale:** no capacity planning for storage.
3. **Integration:** nearly every AWS service reads from or writes to S3 (CloudTrail, ALB logs, Athena, Lambda, EMR, CloudFront, Backup).
4. **Cost tiers:** storage classes from hot to archive.
5. **Security controls:** IAM, bucket policies, encryption, Block Public Access, Object Lock.
6. **Automation:** lifecycle rules, events and replication.

### 1.3 Common DevOps use cases

1. Build **artifacts** (JAR, container-related bundles, Helm charts, Terraform plans).
2. **Terraform remote state** (with locking).
3. Centralised **logs** (ALB, CloudTrail, VPC Flow Logs, application logs).
4. **Backups** (database dumps, EBS snapshot exports, etcd/Velero backups).
5. **Static websites** and frontend assets, typically behind CloudFront.
6. **Data lake** storage for analytics.
7. Software distribution and **disaster recovery** copies.

### 1.4 Real-world example: Jenkins artifact flow

```text
Developer -> Git -> Jenkins
                      |  mvn clean package, tests, scans
                      v
        aws s3 cp target/app.jar s3://company-prod-artifacts/releases/<build>/app.jar
                      |
        Deployment job downloads the exact artifact for that build
        (versioning + lifecycle rules manage old copies)
```

### 1.5 Interview pointers

Q1 (what is S3), Q3 (is S3 a file system).

## 2. Core Concepts and Terminology

### 2.1 Building blocks

| Term | Meaning | Example |
| --- | --- | --- |
| **Bucket** | Top-level container for objects, created in one Region | `company-prod-artifacts` |
| **Object** | The data plus its metadata and key | `app-1.2.0.jar` |
| **Key** | Full name of an object inside a bucket | `releases/2026/10/app-1.2.0.jar` |
| **Prefix** | Leading part of a key, used to group objects and in policies/lifecycle rules | `releases/2026/` |
| **Metadata** | System metadata (content type, length, ETag) and user metadata (`x-amz-meta-*`) | `Content-Type: application/java-archive` |
| **Version ID** | Identifier of one version of an object when versioning is on | `3HL4kqtJlcpXroDTDmJ...` |
| **ETag** | Identifier for object content (an MD5 for simple uploads without KMS; different for multipart/KMS, so not always a checksum) | `"9b2cf535..."` |
| **Region** | Where the bucket and its data physically live | `ap-south-1` |
| **Storage class** | Cost/performance tier of an object | `STANDARD`, `GLACIER` |

### 2.2 Important rules and facts (verify current limits in the documentation)

1. **Bucket names are globally unique** within an AWS partition, 3–63 characters, lowercase letters, numbers, dots and hyphens. They are **not secret**, so never put sensitive data in them.
2. A bucket **cannot be renamed** after creation. Create a new one and copy the data.
3. A bucket belongs to **one Region**. Data does not leave the Region unless you replicate or copy it.
4. A bucket can hold an unlimited number of objects. There is a default **quota on the number of buckets per account** (verify the current value).
5. **Maximum object size is 5 TB.** A single `PUT` upload can be at most **5 GB**, so objects larger than that **must** use **multipart upload**. AWS recommends multipart for objects above about 100 MB.
6. The `/` in a key is just a character. The Console shows "folders" for convenience, but there is no directory hierarchy. "Renaming a folder" means copying and deleting every object under that prefix.
7. Keys can be up to 1,024 bytes (UTF-8). Avoid unusual characters to prevent client and URL-encoding problems.
8. Objects are **immutable**: to change an object you upload a new one with the same key (a new version if versioning is on).
9. **Directory buckets** (used by S3 Express One Zone) are a different bucket type with different behaviour. These notes focus on **general purpose buckets**.

### 2.3 Bucket naming convention example

```text
<company>-<env>-<purpose>-<region>-<account-short-id>
example: acme-prod-artifacts-aps1-1234
```

Include environment and purpose, avoid personal or sensitive information, and add a Region or account suffix to make the name unique.

### 2.4 Key design example

```text
logs/<service>/<yyyy>/<mm>/<dd>/<hh>/file.gz     # time-partitioned, easy lifecycle and Athena partitioning
releases/<app>/<version>/app.jar                 # immutable, versioned path
temporary-builds/<job>/<build-number>/...        # short-retention prefix for lifecycle expiry
```

### 2.5 Common mistakes

1. Assuming S3 behaves like a file system (renaming, appending, locking).
2. Putting secrets or customer names in bucket names.
3. Overwriting a shared key like `releases/latest/app.jar` instead of using versioned paths.
4. Not planning prefixes for lifecycle rules and permissions.

### 2.6 Interview pointers

Q2 (bucket, object, key), Q7 (size limits).

## 3. How S3 Works: Architecture, Durability and Consistency

### 3.1 Request flow

```text
Client (CLI / SDK / app / AWS service)
   |  HTTPS request signed with SigV4 (credentials or presigned URL)
   v
S3 Regional endpoint  (s3.<region>.amazonaws.com or bucket virtual-hosted-style name)
   |  1. Authenticate caller
   |  2. Evaluate permissions: IAM + bucket policy + SCP + VPC endpoint policy + ACL (if enabled) + Block Public Access
   |  3. If SSE-KMS: call AWS KMS (permission and quota checks)
   v
S3 stores or fetches the object across multiple devices in at least three Availability Zones (for most classes)
   |
   v
Response (HTTP status, headers, body)
```

### 3.2 Durability vs availability

1. **Durability:** the probability that data is **not lost**. S3 is designed for **99.999999999% (11 nines)** durability of objects over a year, by storing redundant copies across multiple devices and (for most classes) across at least three AZs.
2. **Availability:** the probability that you can **access** the data when you ask. This differs by storage class (for example, S3 Standard is designed for 99.99%, One Zone-IA lower). Verify current design targets and SLAs.
3. Durability does **not** protect you from **your own mistakes** (deleting, overwriting, a bad lifecycle rule or a compromised credential). That is why you use versioning, Object Lock, replication and least privilege.

### 3.3 Consistency model

1. Since December 2020, S3 provides **strong read-after-write consistency** for `PUT` (new objects and overwrites), `DELETE`, and `LIST` operations, in all Regions, at no extra cost.
2. Practical meaning: after a successful write, a read or list returns the latest data. You no longer need workarounds such as EMRFS consistent view.
3. Concurrent writers to the same key follow **last writer wins** (by request timestamps), and S3 does not provide object locking. Use versioning, conditional writes or application logic where concurrency matters (S3 supports conditional writes such as `If-None-Match`; verify current feature details).

### 3.4 Key behaviours worth remembering

1. **Requests scale by prefix.** S3 supports at least **3,500 write (PUT/COPY/POST/DELETE) and 5,500 read (GET/HEAD) requests per second per prefix**, and a bucket can use many prefixes. Verify current figures.
2. **HTTP 503 Slow Down** means you exceeded a request rate for a partition. Retry with exponential backoff and spread the load across prefixes.
3. **Data transfer in** from the internet is free. Transfer **out**, and some inter-Region/AZ transfers, are charged. Verify pricing.
4. Defaults on **new buckets** (since 2023): **Block Public Access on**, **ACLs disabled** (bucket owner enforced), and **default encryption with SSE-S3** for new objects. Verify the current defaults and that older buckets may differ.

### 3.5 Interview pointers

Q5 (consistency), Q6 (durability vs availability).

## 4. Storage Classes

### 4.1 What it is and why it exists

A storage class sets the **cost, retrieval speed and availability** for an object. Access patterns differ: build artifacts from today are "hot", but a three-year-old log is "cold". Matching the class to the pattern saves money.

### 4.2 Classes (verify current names, minimums and prices)

| Class | Use | Retrieval | Min storage duration | Notes |
| --- | --- | --- | --- | --- |
| **S3 Standard** | Frequently accessed data | Immediate | None | Default. 3+ AZs |
| **S3 Intelligent-Tiering** | Unknown or changing access patterns | Immediate for frequent/infrequent/archive-instant tiers; optional archive tiers need restore | None | Small per-object monitoring fee; automatic tiering; no retrieval fee |
| **S3 Standard-IA** | Infrequent access, but needs millisecond access | Immediate (retrieval fee) | 30 days | Cheaper storage, per-GB retrieval charge, minimum billable object size (128 KB at time of writing) |
| **S3 One Zone-IA** | Infrequent, recreatable data | Immediate (retrieval fee) | 30 days | **One AZ only**, lower resilience |
| **S3 Glacier Instant Retrieval** | Archive that is rarely read but needs milliseconds | Milliseconds | 90 days | Cheap storage, higher retrieval cost |
| **S3 Glacier Flexible Retrieval** | Archive, minutes to hours retrieval | Minutes to hours (restore required) | 90 days | Expedited/standard/bulk restore options |
| **S3 Glacier Deep Archive** | Long-term compliance archive | Hours (restore required) | 180 days | Lowest storage cost |
| **S3 Express One Zone** | Very low latency, high request rates in one AZ | Single-digit milliseconds | None | Directory buckets; specialised |

### 4.3 How to choose

1. Unknown pattern: **Intelligent-Tiering** (accept the monitoring fee, avoid retrieval surprises).
2. Known hot then cold: **Standard** then **lifecycle** to IA or Glacier classes.
3. Easily recreated and non-critical: **One Zone-IA**.
4. Must keep for years, rarely read: **Glacier Flexible or Deep Archive**.
5. Always check **minimum duration**, **minimum object size**, and **retrieval charges**. Moving many tiny objects to IA or Glacier can **increase** cost.

### 4.4 Restore from Glacier classes

1. Objects in Glacier Flexible Retrieval and Deep Archive are **not directly readable**. You submit a **restore request** that creates a temporary readable copy for a number of days.
2. `GET` before restore returns an `InvalidObjectState` error.

```bash
aws s3api restore-object --bucket <bucket> --key archive/data.zip \
  --restore-request '{"Days":7,"GlacierJobParameters":{"Tier":"Standard"}}'
aws s3api head-object --bucket <bucket> --key archive/data.zip    # check the "Restore" field
```

### 4.4.1 Setting a class at upload

```bash
aws s3 cp backup.tar.gz s3://<bucket>/backups/ --storage-class STANDARD_IA
```

### 4.5 Common mistakes

1. Transitioning small objects to IA/Glacier and paying minimum-size and request costs.
2. Deleting objects before the minimum storage duration and paying for the full period.
3. Forgetting that archived objects need restore time in an incident.
4. Using One Zone-IA for the only copy of important data.

### 4.6 Interview pointers

Q4 (storage classes), Q9 (lifecycle), Q33 (cost).

## 5. Versioning and Delete Markers

### 5.1 What it is

1. **Versioning** keeps **multiple versions** of an object in the same bucket. Every overwrite creates a new version with a unique **version ID**.
2. States: **unversioned** (default for older setups), **enabled**, **suspended**. You **cannot return** a bucket to unversioned once enabled. You can only suspend.

### 5.2 Why it is needed

1. Recover from **accidental delete or overwrite**.
2. Keep history of artifacts or configuration files.
3. Required for **replication** and **Object Lock**.

### 5.3 How it works (step by step)

1. Upload `app.jar`: version `v1` is stored and becomes the **current** version.
2. Upload `app.jar` again: `v2` becomes current, and `v1` becomes a **noncurrent** version. Both are stored and billed.
3. **Delete** `app.jar` (without a version ID): S3 adds a **delete marker** as the newest version. The object **appears deleted** (a plain GET returns 404), but all versions still exist.
4. **Recover** by deleting the delete marker (by its version ID). The previous version becomes current again.
5. **Permanently delete** by specifying a version ID: `DeleteObject` with `versionId`. This cannot be undone.

```text
Key: app.jar
  [delete marker]  (current)   <- plain GET returns 404
  v2                           <- noncurrent
  v1                           <- noncurrent

Remove the delete marker -> v2 becomes current again.
```

### 5.4 Commands

```bash
aws s3api put-bucket-versioning --bucket <bucket> --versioning-configuration Status=Enabled
aws s3api list-object-versions --bucket <bucket> --prefix releases/app.jar
# Recover: delete the delete marker (use the DeleteMarker's VersionId)
aws s3api delete-object --bucket <bucket> --key releases/app.jar --version-id <delete-marker-version-id>
# Or restore an older version by copying it back as the newest version
aws s3api copy-object --bucket <bucket> --key releases/app.jar \
  --copy-source "<bucket>/releases/app.jar?versionId=<old-version-id>"
```

### 5.5 Production notes

1. **[MANDATORY]** Enable versioning on buckets that hold important data (artifacts, state, backups).
2. Pair it with **lifecycle rules** to expire noncurrent versions, otherwise storage and cost grow forever.
3. **[OPTIONAL]** Enable **MFA Delete** (can only be turned on by the root user with the CLI/API) for extra protection against deletion of versions. Many teams prefer **Object Lock** and strict IAM instead.
4. Terraform state buckets **must** have versioning enabled so you can recover a corrupted or overwritten state file.

### 5.6 Common mistakes

1. Thinking a delete marker means the data is gone.
2. Enabling versioning and never expiring old versions.
3. Listing with `aws s3 ls` and missing versions (use `list-object-versions`).
4. Believing versioning protects against deleting a **version** by an over-privileged user (it does not, only Object Lock/MFA Delete/IAM do).

### 5.7 Interview pointers

Q8 (versioning), Q29 (recover deleted object).

## 6. Lifecycle Management

### 6.1 What it is

Lifecycle rules **automatically transition objects between storage classes or expire (delete) them** after a set time, based on a prefix, tag or size filter.

### 6.2 Why it is needed

1. Control cost without manual cleanup.
2. Move cold data to cheaper classes.
3. Enforce retention periods (delete logs after N days).
4. Clean up **incomplete multipart uploads** and **noncurrent versions**.

### 6.3 Rule actions

| Action | Meaning |
| --- | --- |
| **Transition** | Move current objects to another class after N days (for example Standard to Standard-IA at 30 days) |
| **NoncurrentVersionTransition** | Move noncurrent versions to another class |
| **Expiration** | Delete current objects after N days. In a **versioned** bucket this **adds a delete marker**, it does not remove versions |
| **NoncurrentVersionExpiration** | **Permanently delete** noncurrent versions after N days (optionally keep the newest N noncurrent versions) |
| **ExpiredObjectDeleteMarker** | Remove a delete marker when no versions remain under it |
| **AbortIncompleteMultipartUpload** | Delete leftover parts of uploads not completed within N days |

### 6.4 Rules to remember

1. Objects have **minimum durations** before certain transitions (for example, a minimum of 30 days in Standard before moving to Standard-IA or One Zone-IA, verify current rules).
2. Lifecycle runs **asynchronously**, usually once a day, so actions do not happen at the exact second. Billing for expired objects stops when they become eligible for expiry.
3. A lifecycle rule applies to objects matching its **filter**. A rule with an empty filter applies to the **whole bucket**, so be careful.
4. Lifecycle can delete data **permanently**. **[MANDATORY]** Review retention requirements before enabling expiration, and test on a non-production prefix first.

### 6.5 Example (JSON)

```json
{
  "Rules": [
    {
      "ID": "logs-tiering-and-expiry",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

```bash
aws s3api put-bucket-lifecycle-configuration --bucket <bucket> --lifecycle-configuration file://lifecycle.json
aws s3api get-bucket-lifecycle-configuration --bucket <bucket>
```

What it does: logs move to Standard-IA after 30 days, Glacier after 90, are deleted at 365 days, noncurrent versions are deleted after 30 days, and abandoned multipart uploads are cleaned after 7 days.

### 6.6 Common mistakes

1. Expiration rule on the wrong prefix (a real cause of "our releases disappeared").
2. Forgetting noncurrent-version rules in a versioned bucket, so cost grows.
3. Transitioning many tiny objects (request charges and minimum sizes).
4. Not aborting incomplete multipart uploads.

### 6.7 Interview pointers

Q9 (lifecycle), Q33 (cost), Q29 (deletion by lifecycle).

## 7. Access Control and Security

### 7.1 Layers of S3 access control

A request must pass **every** applicable layer. An **explicit Deny anywhere wins**.

| Layer | What it does |
| --- | --- |
| **IAM identity policy** | Allows or denies actions for a user or role |
| **Bucket policy** (resource policy) | JSON policy on the bucket; can allow other accounts, enforce TLS/encryption/VPC conditions |
| **Block Public Access (BPA)** | Account- or bucket-level override that blocks public policies/ACLs |
| **Object Ownership / ACLs** | Legacy per-object permissions. **Disabled by default on new buckets** (bucket owner enforced) |
| **SCP / permission boundary** | Organization or identity-level limits |
| **VPC endpoint policy** | Limits what can be done through an endpoint |
| **Access points** | Named endpoints with their own policies for different applications |
| **KMS key policy** | Required if the objects use SSE-KMS |

### 7.2 IAM policy vs bucket policy

| Feature | IAM policy | Bucket policy |
| --- | --- | --- |
| Attached to | User, group, role | Bucket |
| `Principal` element | Not used | Required |
| Best for | What **this identity** may do across resources | Who may access **this bucket** (including other accounts), and bucket-wide conditions |
| Cross-account | Needs the bucket side to allow too | Can grant another account's principal access directly |
| Size limit | Quota per policy | 20 KB |

Same-account access is allowed if **either** the identity policy or the bucket policy allows it (and nothing denies). **Cross-account** access needs **both** sides to allow it (identity policy in the caller's account, bucket policy in the bucket owner's account).

### 7.3 Bucket vs object ARN (a classic bug)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-prod-artifacts",
      "Condition": { "StringLike": { "s3:prefix": ["releases/*"] } }
    },
    {
      "Sid": "ReadWriteObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-prod-artifacts/releases/*"
    }
  ]
}
```

1. `s3:ListBucket` applies to the **bucket ARN** (no `/*`).
2. `s3:GetObject` and `s3:PutObject` apply to the **object ARN** (`bucket/key-pattern`).
3. Mixing them up produces `AccessDenied` even though the policy "looks right".

### 7.4 Block Public Access

1. Four settings: `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, `RestrictPublicBuckets`.
2. Applies at **account level** and **bucket level**. The most restrictive wins.
3. **[MANDATORY]** Turn on **all four** at the **account level** (and per bucket), unless a bucket is deliberately public (for example, direct public static hosting, which is better served through CloudFront anyway).

### 7.5 Object Ownership and ACLs

1. **Bucket owner enforced** (recommended, default for new buckets): ACLs are **disabled**, and the bucket owner owns all objects. Access is controlled only by policies.
2. Older settings let uploaders own objects, which causes "I can't read objects another account uploaded" problems.
3. **[MANDATORY]** Prefer policies over ACLs. Use ACLs only for specific legacy needs (for example, some log-delivery setups; verify current requirements).

### 7.6 VPC endpoints and data perimeter

1. A **gateway endpoint** for S3 keeps traffic from private subnets on the AWS network without NAT (route table entry, no charge for the endpoint itself).
2. An **interface endpoint** for S3 (PrivateLink) lets on-premises or other VPC networks reach S3 privately over VPN/Direct Connect. It has hourly and data charges.
3. Use **endpoint policies** and bucket policy conditions (`aws:SourceVpce`, `aws:SourceVpc`, `aws:PrincipalOrgID`) to build a **data perimeter**: only your organisation's identities, from your networks, can reach the data. Test carefully to avoid locking out CI, console and break-glass access.

```json
{
  "Sid": "DenyUnlessFromOurVpce",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::company-prod-data", "arn:aws:s3:::company-prod-data/*"],
  "Condition": { "StringNotEquals": { "aws:SourceVpce": "vpce-0123456789abcdef0" } }
}
```

This is a **placeholder example**. A blanket Deny like this also blocks the console, CI and administrators outside the VPC unless you add exceptions (for example by principal or tag).

### 7.7 Presigned URLs

1. A presigned URL gives **temporary access to one object** (GET or PUT) to someone without AWS credentials.
2. It is signed with the **credentials of the creator** and carries that creator's permissions. If the creator loses permission, the URL stops working.
3. **Expiry:** up to **7 days** when signed with IAM user credentials (SigV4). When created with **temporary role credentials**, it expires when the session credentials expire, even if you asked for longer.
4. Treat a presigned URL as a **bearer secret**: anyone with the link can use it until it expires. Keep expiry short and avoid logging full URLs.
5. Use cases: let a browser upload directly to S3, share a report for one hour.

### 7.8 S3 Object Lock (WORM)

1. **WORM** means **Write Once, Read Many**. Object Lock prevents object versions from being deleted or overwritten for a **retention period** or until a **legal hold** is removed.
2. Requires **versioning**. It protects **specific versions**.
3. Modes:
   - **Governance:** most users cannot delete or shorten retention, but users with the special permission (`s3:BypassGovernanceRetention`) can.
   - **Compliance:** **nobody**, **not even the root user**, can delete the version or shorten retention until it expires.
   - **Legal hold:** indefinite lock with no retention date, removed by someone with `s3:PutObjectLegalHold`.
4. Use for regulatory retention (financial, healthcare) and **ransomware protection** of backups.
5. **Caution:** Compliance mode is irreversible for the retention period. Test with Governance mode first. Verify the current rules for enabling Object Lock on existing buckets.

### 7.9 Other security features

1. **IAM Access Analyzer for S3:** finds buckets shared publicly or with other accounts.
2. **Amazon Macie:** discovers sensitive data (PII) in S3.
3. **GuardDuty S3 protection:** detects suspicious access patterns.
4. **S3 Access Grants, Access Points, Multi-Region Access Points:** advanced access management (verify current feature details).

### 7.10 Common mistakes

1. Public bucket policy `"Principal": "*"` without conditions.
2. Using access keys in CI instead of roles.
3. Missing the bucket-vs-object ARN split.
4. Forgetting KMS permissions when objects use SSE-KMS.
5. Locking yourself out with an over-strict Deny policy.

### 7.11 Interview pointers

Q10 (IAM vs bucket policy), Q11 (BPA and ACLs), Q13 (presigned URLs), Q17 (EC2 access), Q19 (Object Lock), Q20 (cross-account), Q26 (access points), Q37 (data perimeter).

## 8. Encryption

### 8.1 Encryption in transit

1. S3 supports HTTPS (TLS). **[MANDATORY]** Enforce it with a bucket policy that denies requests where `aws:SecureTransport` is `false`.
2. You can also require a **minimum TLS version** with the `s3:TlsVersion` condition (verify current support).

### 8.2 Encryption at rest

All new objects are encrypted at rest by default (SSE-S3 unless you choose otherwise). Options:

| Option | Who manages keys | Notes |
| --- | --- | --- |
| **SSE-S3** | S3 | Default. No extra cost. Simple. No key-level audit or per-key access control |
| **SSE-KMS** | You control a KMS key (AWS managed `aws/s3` or customer managed) | Key policy and grants, CloudTrail logs of key use, key rotation. Adds KMS request cost and quotas |
| **DSSE-KMS** | KMS, with **two layers** of encryption | For specific compliance needs |
| **SSE-C** | **You supply** the key on every request | AWS does not store the key. Lose it and the data is gone. Rarely used. Verify current availability/default settings |
| **Client-side encryption** | You encrypt before upload | S3 only sees ciphertext |

### 8.3 SSE-S3 vs SSE-KMS

| Feature | SSE-S3 | SSE-KMS |
| --- | --- | --- |
| Key control | AWS-owned and managed | You control key policy, can disable key |
| Audit of key use | No per-use trail | CloudTrail records KMS API use |
| Cross-account | Simple | Key policy and grants must allow the other account |
| Cost | None | KMS request charges |
| Throttling | None | KMS request-rate quotas can throttle high-volume workloads |
| Typical use | General data | Regulated data, need key-level control or audit |

### 8.4 S3 Bucket Keys

1. With SSE-KMS every object operation can call KMS. **S3 Bucket Keys** let S3 use a bucket-level key to generate object keys, which can cut KMS requests (and cost) by a large factor.
2. **[OPTIONAL]** Enable Bucket Keys on SSE-KMS buckets with many objects. Note that CloudTrail KMS events then show the bucket-level key rather than per-object calls.

### 8.5 KMS permission gotchas

For SSE-KMS the caller needs both S3 permissions **and** KMS permissions:

1. Upload: `kms:GenerateDataKey` (and `kms:Decrypt` in some multipart cases).
2. Download: `kms:Decrypt`.
3. The **key policy** must allow the principal (or delegate to IAM). For **cross-account** access the key policy of the owning account must allow the other account.
4. A disabled key, or a key in a different Region than expected, produces `AccessDenied` or `KMS.*` errors.

### 8.6 Enforcing encryption

```json
{
  "Sid": "DenyUnencryptedTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::company-prod-artifacts", "arn:aws:s3:::company-prod-artifacts/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

To require SSE-KMS, set the bucket **default encryption** to SSE-KMS (preferred) and optionally deny `PutObject` requests whose `s3:x-amz-server-side-encryption` header is not `aws:kms`. Check how clients (and replication) behave before adding such a deny.

### 8.7 Common mistakes

1. SSE-KMS with no `kms:Decrypt` on the consumer role.
2. Cross-account reads of KMS-encrypted objects without updating the key policy.
3. KMS request throttling under high load (use Bucket Keys, spread load).
4. Deleting or disabling a KMS key and losing access to the data.
5. Using SSE-C and losing the keys.

## 9. Uploads, Multipart and Performance

### 9.1 Upload options

| Method | Use |
| --- | --- |
| Single `PutObject` | Objects up to 5 GB (practical for small objects) |
| **Multipart upload** | Large objects (recommended above ~100 MB, **required** above 5 GB), up to 5 TB |
| Presigned URL upload | Browsers and clients without AWS credentials |
| `aws s3 cp/sync` | The high-level CLI automatically uses multipart for large files |
| Transfer Acceleration | Faster long-distance uploads through edge locations (extra cost) |
| AWS DataSync / Snow family | Bulk migration |

### 9.2 How multipart upload works

1. **Initiate** the upload and receive an **upload ID**.
2. **Upload parts** (each 5 MiB to 5 GiB, except the last part, up to 10,000 parts) in parallel. Each part returns an ETag.
3. **Complete** the upload by sending the ordered part list. S3 assembles the object.
4. If something fails, **retry only the failed part**.
5. If never completed or aborted, the uploaded parts **stay and are billed**. Use a lifecycle rule `AbortIncompleteMultipartUpload`.

Benefits: higher throughput (parallel parts), resilience (retry a part), ability to pause and resume, and uploading while the size is still unknown.

```bash
# See leftover incomplete uploads (a hidden cost source)
aws s3api list-multipart-uploads --bucket <bucket>

# Tune CLI multipart behaviour
aws configure set default.s3.multipart_threshold 64MB
aws configure set default.s3.multipart_chunksize 64MB
aws configure set default.s3.max_concurrent_requests 20
```

### 9.3 Data integrity

1. S3 supports additional **checksums** (CRC32, CRC32C, SHA-1, SHA-256 and others, verify current list). Newer SDK/CLI versions compute them by default for uploads.
2. For artifact pipelines, store and verify a **SHA-256** so a deployment confirms it fetched the exact build.
3. Do **not** assume the ETag is an MD5 of the file (it is not for multipart or SSE-KMS objects).

### 9.4 Performance guidance

1. **Parallelise:** many connections and multipart parts. Use byte-range GETs to download large objects in parallel.
2. **Spread across prefixes** if you need very high request rates (limits are per prefix).
3. Handle **503 Slow Down** with exponential backoff and jitter (AWS SDKs do this by default).
4. Place compute in the **same Region** as the bucket. Use **CloudFront** to cache and speed up downloads. Use **Transfer Acceleration** for uploads from distant clients.
5. For many small files, **batch** (for example tar or compress) to reduce request overhead and cost.
6. **Mountpoint for Amazon S3** presents a bucket as a local file-like path for read-heavy workloads, but it is **not** a full POSIX file system (verify supported operations).
7. S3 **Express One Zone** targets single-digit-millisecond latency for ML and analytics workloads (verify current feature and pricing).

### 9.5 Common mistakes

1. Single-threaded upload of huge files.
2. Never cleaning incomplete multipart uploads.
3. Hot-spotting a single prefix.
4. Using S3 as a low-latency database.

## 10. Replication: SRR and CRR

### 10.1 What it is

**S3 Replication** automatically and asynchronously copies new objects from a **source bucket** to one or more **destination buckets**.

| Type | Meaning | Typical reason |
| --- | --- | --- |
| **SRR** (Same-Region Replication) | Source and destination in the same Region | Log aggregation into one account, separate prod/test copy, data-sovereignty, a backup copy in another account |
| **CRR** (Cross-Region Replication) | Destination in a different Region | Disaster recovery, lower latency for remote users, compliance with geographic separation |

Replication works **across accounts** too, which is a strong pattern for protecting backups from a compromised source account.

### 10.2 How it works (step by step)

1. Enable **versioning** on **both** buckets (**mandatory**).
2. Create an **IAM role** that S3 assumes. It needs read on the source and replicate permissions on the destination (plus KMS permissions if encrypted).
3. Create a **replication rule** with a filter (whole bucket, prefix or tags) and a destination (optionally with a different storage class or owner).
4. New objects matching the rule are replicated **asynchronously** (usually within seconds to minutes, but there is no guarantee unless you use **Replication Time Control**).
5. Each source object has a **replication status**: `PENDING`, `COMPLETED`, `FAILED`, or `REPLICA` on the destination.

```text
Source bucket (ap-south-1, versioning ON)
   |  replication rule + IAM role
   v
Destination bucket (ap-southeast-1, versioning ON)   <- objects arrive with status REPLICA
```

### 10.3 Important behaviours

1. **Existing objects are not replicated** by a new rule. Use **S3 Batch Replication** to copy existing objects or retry failed ones.
2. **Replication is not chained** by default: if A replicates to B and B replicates to C, objects replicated into B (replicas) are not replicated again to C.
3. **Delete markers** can be replicated if you enable that option. **Permanent deletes of a specific version are not replicated**, which protects the destination from malicious deletion.
4. Lifecycle actions in the source are **not** replicated as deletes (configure lifecycle separately on each bucket).
5. **SSE-KMS** objects can be replicated, but you must enable it in the rule and give the role KMS permissions on both source and destination keys.
6. **Replication Time Control (RTC)** adds an SLA-backed target (replicating most objects within 15 minutes) with metrics and event notifications, at extra cost. Verify current terms.
7. You can change **ownership** to the destination account owner and change the **storage class** (for example Glacier at the destination).
8. Bi-directional replication is possible (with replica modification sync), but it needs careful design to avoid conflicts.
9. Replication **is not a backup by itself**: if a bad overwrite is replicated, both copies are bad. Use versioning and Object Lock on the destination.

### 10.4 Common mistakes

1. Versioning not enabled on the destination.
2. IAM role missing KMS permissions, so encrypted objects fail.
3. Expecting old objects to appear automatically.
4. Destination bucket policy blocks the replication role.
5. Expecting replication to protect against all deletion.

### 10.5 Interview pointers

## 11. Static Website Hosting and CloudFront

### 11.1 S3 static website hosting

1. S3 can serve **static content** (HTML, CSS, JS, images) from a bucket through the **website endpoint**, with an index document and an error document.
2. The website endpoint supports **HTTP only**, **no HTTPS**, no custom domain TLS, and requires objects to be publicly readable if you use it directly.
3. Direct public hosting conflicts with the modern default of Block Public Access, so for production it is **not** the preferred pattern.

### 11.2 Recommended production pattern: CloudFront with Origin Access Control

```text
User -> Route 53 -> CloudFront (HTTPS, caching, WAF, custom domain via ACM certificate)
                        |  Origin Access Control (OAC), signed requests
                        v
                 PRIVATE S3 bucket (Block Public Access ON)
                 bucket policy allows only this CloudFront distribution
```

1. Keep the bucket **private** with Block Public Access on.
2. Use the S3 **REST endpoint** as the CloudFront origin and **OAC** (the modern replacement for Origin Access Identity).
3. Bucket policy allows `s3:GetObject` only to the CloudFront service principal with `AWS:SourceArn` equal to your distribution ARN.
4. Add an **ACM certificate** (in `us-east-1` for CloudFront), HTTPS redirect, caching, WAF and logging.
5. For single-page apps, map 403/404 responses to `index.html` in CloudFront custom error responses.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontOAC",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-prod-site/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EXAMPLEDISTID"
        }
      }
    }
  ]
}
```

`123456789012` and `EXAMPLEDISTID` are placeholders. Replace them with your account ID and distribution ID.

### 11.3 Common mistakes

1. Making the bucket public to "make the site work".
2. Using the website endpoint as an OAC origin (OAC works with the REST endpoint, and the website endpoint needs a different approach).
3. Forgetting cache invalidation after deployments (use versioned file names or invalidate paths).
4. Certificate created in the wrong Region for CloudFront.

## 12. Event Notifications and Integrations

### 12.1 S3 Event Notifications

1. S3 can emit events (for example `s3:ObjectCreated:*`, `s3:ObjectRemoved:*`, lifecycle and replication events) to **SNS**, **SQS**, **Lambda** or **Amazon EventBridge**.
2. Filters by **prefix and suffix** limit which objects trigger events.
3. Typical pattern: image uploaded to `uploads/` -> Lambda creates thumbnails -> writes to `thumbnails/`.

```text
Upload -> S3 (ObjectCreated, prefix uploads/) -> SQS queue -> workers (retry, DLQ, throttling)
```

### 12.2 Production notes

1. **Never** write results into the **same prefix** that triggers the event, or you create an **infinite loop** and a large bill.
2. Prefer **SQS** between S3 and consumers for buffering, retries and a dead-letter queue.
3. Delivery is **at least once**. Make consumers idempotent.
4. **EventBridge** gives richer filtering and more targets (verify current features).
5. Permissions: the destination (SQS/SNS/Lambda) needs a **resource policy** that allows S3 to send.

### 12.3 Other integrations

| Service | Purpose with S3 |
| --- | --- |
| **Athena** | SQL queries on data in S3 |
| **Glue** | Data catalog and ETL |
| **CloudFront** | Cache and secure delivery |
| **AWS Backup** | Central backups of S3 |
| **S3 Batch Operations** | Run an action (copy, tag, restore, invoke Lambda) over millions of objects from an inventory list |
| **S3 Inventory** | Scheduled CSV/Parquet listing of objects and metadata |
| **Transfer Family / DataSync** | SFTP access and bulk transfer |

## 14. Pricing and Cost Optimization

### 14.1 What you pay for (verify current prices)

1. **Storage** (GB-month, by class).
2. **Requests** (PUT/COPY/POST/LIST are priced higher than GET). Lifecycle transitions are also requests.
3. **Data transfer out** to the internet and some inter-Region transfers. Transfer in is free. Transfer to CloudFront from S3 in the same Region is free of S3 transfer charges (CloudFront has its own pricing).
4. **Retrieval** fees for IA and Glacier classes.
5. **Management features:** Inventory, Storage Lens advanced metrics, Object Lambda, Intelligent-Tiering monitoring.
6. **Replication:** destination storage, requests, inter-Region transfer, RTC.
7. **KMS** request charges for SSE-KMS.
8. **CloudTrail data events**, **server access logs** storage.
9. **Incomplete multipart uploads** and **noncurrent versions**, which still count as stored data.

### 14.2 Cost optimisation checklist

1. **Lifecycle rules** for logs and temporary data. Include noncurrent version expiry and multipart abort.
2. **Intelligent-Tiering** for unpredictable access.
3. Avoid transitioning **tiny objects** to IA/Glacier. Compact them first.
4. Respect **minimum storage durations** to avoid early-deletion charges.
5. Use **S3 Gateway endpoints** so private workloads do not pay NAT data processing for S3 traffic.
6. Use **CloudFront** for repeated downloads to reduce data transfer and request costs.
7. Use **Bucket Keys** for SSE-KMS.
8. Use **Storage Lens** and **Cost Explorer** (group by usage type, bucket tags) to find drivers.
9. Delete unused buckets, old inventories and abandoned logs.
10. Keep traffic **in-Region** where possible. Cross-Region replication and reads cost transfer fees.
11. For **requester-pays** scenarios (sharing large public datasets), enable **Requester Pays** so downloaders pay the transfer.

### 14.3 Investigating a cost spike (order of checks)

1. Cost Explorer: group by **service > usage type > bucket (cost allocation tags) > Region**.
2. Compare **storage growth** (CloudWatch `BucketSizeBytes` by storage type) with the previous month.
3. Look for **noncurrent versions** and **incomplete multipart uploads** (Storage Lens).
4. Check **request** counts and **data transfer out** (unexpected downloads, hot-linking, a crawler, a runaway job).
5. Check **replication** and **logging** traffic.
6. Check **KMS** and **CloudTrail data events** charges.
7. Apply a tested fix (lifecycle, caching, endpoint) and track the next bill.

## 15. Hands-On: CLI, Terraform, Jenkins and Python

### 15.1 AWS CLI: `s3` vs `s3api`

1. `aws s3` are **high-level** commands (`ls`, `cp`, `mv`, `rm`, `sync`) with automatic multipart and parallelism.
2. `aws s3api` are **low-level** commands that map one-to-one to S3 API operations (`put-bucket-policy`, `list-object-versions`, `head-object`).

Prerequisites: AWS CLI v2, authentication through **SSO or an assumed role**, and a Region. Always start with the identity check.

```bash
aws sts get-caller-identity                    # which account and role am I using?
export AWS_REGION=ap-south-1                   # placeholder

# ----- Buckets -----
aws s3 ls                                      # list buckets

# Create a bucket (outside us-east-1 a LocationConstraint is required; in us-east-1 omit it)
aws s3api create-bucket --bucket <unique-bucket-name> --region ap-south-1 \
  --create-bucket-configuration LocationConstraint=ap-south-1

# Baseline settings
aws s3api put-public-access-block --bucket <bucket> --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws s3api put-bucket-versioning --bucket <bucket> --versioning-configuration Status=Enabled

# Inspect (read-only)
aws s3api get-bucket-location            --bucket <bucket>
aws s3api get-bucket-versioning          --bucket <bucket>
aws s3api get-bucket-encryption          --bucket <bucket>
aws s3api get-public-access-block        --bucket <bucket>
aws s3api get-bucket-policy              --bucket <bucket>
aws s3api get-bucket-ownership-controls  --bucket <bucket>
aws s3api get-bucket-lifecycle-configuration --bucket <bucket>
aws s3api get-bucket-replication         --bucket <bucket>

# ----- Objects -----
aws s3 ls s3://<bucket>/releases/ --recursive --human-readable --summarize
aws s3 cp app.jar s3://<bucket>/releases/1.2.0/app.jar
aws s3 cp s3://<bucket>/releases/1.2.0/app.jar ./app.jar
aws s3 sync ./site s3://<bucket>/ --delete --dryrun      # ALWAYS dry-run --delete first
aws s3api head-object --bucket <bucket> --key releases/1.2.0/app.jar
aws s3api list-object-versions --bucket <bucket> --prefix releases/1.2.0/app.jar

# Temporary download link (1 hour)
aws s3 presign s3://<bucket>/reports/monthly.pdf --expires-in 3600
```

Notes:

1. Commands such as `get-bucket-policy` or `get-bucket-replication` return an error like `NoSuchBucketPolicy` or `ReplicationConfigurationNotFoundError` when nothing is configured. That is not a failure of the bucket. An `AccessDenied` response may also mean **you lack the permission to read** that configuration.
2. `aws s3 sync --delete` removes destination objects not in the source. Run `--dryrun` first.
3. Add `--debug` or `--cli-read-timeout` when diagnosing client issues (avoid sharing debug output because it may expose sensitive information).

### 15.2 Terraform: production-style private artifact bucket

**Assumptions:** Terraform `>= 1.5`, AWS provider `~> 5.0` (verify current versions). Replace placeholder names and tags.

**Folder structure**

s3-artifacts/
├── versions.tf
├── variables.tf
├── main.tf
└── outputs.tf
```

**`versions.tf`**

    }
  }

  region = var.region
}
```

**`variables.tf`**

```hcl
variable "region" {
  type    = string
  default = "ap-south-1" # placeholder
}

variable "bucket_name" {
  type        = string
  description = "Globally unique bucket name"
}

variable "environment" {
  type = string
}

variable "kms_key_arn" {
  type        = string
  description = "Optional customer-managed KMS key ARN. Empty string uses SSE-S3."
  default     = ""
}
```

**`main.tf`**

```hcl
resource "aws_s3_bucket" "artifacts" {
  bucket = var.bucket_name

  tags = {
    Environment = var.environment
    Application = "artifacts"
    ManagedBy   = "terraform"
  }
}

# ACLs disabled; bucket owner owns everything
resource "aws_s3_bucket_ownership_controls" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id
  rule {
    object_ownership = "BucketOwnerEnforced"
  }
}

resource "aws_s3_bucket_public_access_block" "artifacts" {
  bucket                  = aws_s3_bucket.artifacts.id
  block_public_acls       = true
  ignore_public_acls      = true
  block_public_policy     = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_versioning" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id

  rule {
    bucket_key_enabled = var.kms_key_arn != ""

    apply_server_side_encryption_by_default {
      sse_algorithm     = var.kms_key_arn != "" ? "aws:kms" : "AES256"
      kms_master_key_id = var.kms_key_arn != "" ? var.kms_key_arn : null
    }
  }
}

resource "aws_s3_bucket_lifecycle_configuration" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id

  # Short-retention scratch area only. Releases are NOT expired here.
  rule {
    id     = "expire-temporary-builds"
    status = "Enabled"

    filter {
      prefix = "temporary-builds/"
    }

    expiration {
      days = 30
    }

    noncurrent_version_expiration {
      noncurrent_days = 7
    }

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }

  # Whole bucket: clean up noncurrent versions and abandoned uploads
  rule {
    id     = "bucket-hygiene"
    status = "Enabled"

    filter {}

    noncurrent_version_expiration {
      noncurrent_days = 90
    }

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
}

# Deny any non-TLS request
data "aws_iam_policy_document" "artifacts" {
  statement {
    sid     = "DenyInsecureTransport"
    effect  = "Deny"
    actions = ["s3:*"]
    resources = [
      aws_s3_bucket.artifacts.arn,
      "${aws_s3_bucket.artifacts.arn}/*",
    ]
    principals {
      type        = "*"
      identifiers = ["*"]
    }
    condition {
      test     = "Bool"
      variable = "aws:SecureTransport"
      values   = ["false"]
    }
  }
}

resource "aws_s3_bucket_policy" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id
  policy = data.aws_iam_policy_document.artifacts.json

  depends_on = [aws_s3_bucket_public_access_block.artifacts]
}
```

**`outputs.tf`**

```hcl
output "bucket_name" {
  value = aws_s3_bucket.artifacts.id
}

output "bucket_arn" {
  value = aws_s3_bucket.artifacts.arn
}
```

```bash

| Block | Reason |
| --- | --- |

    environment {
        BUCKET = 'company-prod-artifacts'        // placeholder
        PREFIX = "releases/${env.BUILD_NUMBER}"
    }

    stages {
        stage('Build') {
            steps { sh 'mvn -B clean package' }
        }

        stage('Test') {
            steps { sh 'mvn -B test' }
        }

        stage('Checksum') {
            steps {
                sh 'sha256sum target/app.jar > target/app.jar.sha256'
            }
        }

        stage('Upload Artifact') {
            when { branch 'main' }   // untrusted PR builds must not receive cloud credentials
            steps {
                sh '''
                  set -euo pipefail
                  aws sts get-caller-identity                  # fail fast if the role is wrong

                  aws s3 cp target/app.jar        "s3://${BUCKET}/${PREFIX}/app.jar"
                  aws s3 cp target/app.jar.sha256 "s3://${BUCKET}/${PREFIX}/app.jar.sha256"

                  # Verify the object landed and has the expected size
                  aws s3api head-object --bucket "${BUCKET}" --key "${PREFIX}/app.jar" \
                    --query ContentLength --output text
                '''
            }
        }
    }

    post {
        failure { echo 'Pipeline failed: check the stage log above.' }
    }
}
```

What it does and why: tests run **before** publishing, the upload only runs on `main`, the S3 key includes the **build number** (immutable path, no overwrite), a SHA-256 file lets the deploy job verify integrity, and `set -euo pipefail` makes the stage fail on any error.

### 15.4 Python (boto3): presigned URL and safe downloads

```python
#!/usr/bin/env python3
"""Create a short-lived presigned download URL. Uses the default credential chain (role/SSO)."""
import sys

import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

BUCKET = "company-prod-reports"      # placeholder
KEY = "reports/2026/10/monthly.pdf"  # placeholder


def main() -> int:
    s3 = boto3.client("s3", config=Config(signature_version="s3v4", retries={"max_attempts": 5, "mode": "standard"}))
    try:
        s3.head_object(Bucket=BUCKET, Key=KEY)   # confirm the object exists and we may read metadata
        url = s3.generate_presigned_url(
            "get_object",
            Params={"Bucket": BUCKET, "Key": KEY},
            ExpiresIn=900,                        # 15 minutes: keep it short
        )
    except ClientError as exc:
        print(f"S3 error: {exc.response['Error']['Code']}", file=sys.stderr)
        return 1
    print("URL created (treat as a secret; do not log it).")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

Why: the URL carries the **creator's permissions** and expires with the temporary credentials if you used a role. A short expiry reduces risk if it leaks.

## 16. Production Troubleshooting Scenarios

Each scenario follows: **Problem → Symptoms/impact → Possible causes → Investigation → Procedure → Root cause → Resolution → Prevention → How to explain it in an interview.**

### Beginner scenarios

#### A1. `AccessDenied` on upload (`PutObject`)

1. **Problem:** The pipeline cannot upload to the bucket.
2. **Symptoms and impact:** `An error occurred (AccessDenied) when calling the PutObject operation`; the release is blocked.
3. **Possible causes:** Wrong identity or account, missing `s3:PutObject` on the **object ARN**, bucket policy explicit deny (for example required encryption header), SCP or permission boundary, missing KMS permission, wrong bucket/prefix, Block Public Access conflicts, VPC endpoint policy.
4. **Tools:** `aws sts get-caller-identity`, IAM policy simulator, bucket policy, CloudTrail (data events if enabled, or the failed call in management history), KMS key policy.
5. **Procedure:**
   1. Confirm the **identity**. Wrong role or stale environment variables are common.
   2. Confirm the **exact bucket and key** and Region.
   3. Check the identity policy: does `PutObject` target `arn:aws:s3:::bucket/prefix/*`?
   4. Read the bucket policy for **explicit Deny** (TLS, encryption header, source VPC, principal conditions).
   5. If SSE-KMS: check `kms:GenerateDataKey` and the key policy.
   6. Check SCPs and boundaries.
6. **Root cause (typical):** The CI role could write `releases/*` but the job uploaded to `release/` (typo), or the bucket policy denied requests without the required encryption header.
7. **Resolution:** Fix the key path or add the required header/KMS permission, then retest with minimum permissions.
8. **Prevention:** Define bucket path conventions in code, run a policy-simulation step in CI, keep policies in Terraform with reviews.
9. **Interview explanation:** "I verified who I was, then walked the layers from identity policy to bucket policy, KMS and SCP. The error text and CloudTrail pointed to the specific denying layer."

#### A2. Object "disappeared" (accidental delete)

1. **Problem:** A file is missing (HTTP 404).
2. **Possible causes:** A human or script deleted it, a **lifecycle expiration** rule removed it, a bad `sync --delete`, or it never existed under that key.
3. **Procedure:**
   1. Check whether **versioning** is enabled: `get-bucket-versioning`.
   2. `list-object-versions --prefix <key>`: is there a **delete marker** or older versions?
   3. Recover by **deleting the delete marker** or copying the older version back.
   4. Check **CloudTrail** (data events) and lifecycle configuration to see who or what deleted it.
4. **Resolution:** Restore the version. If versioning was off and there is no replica or backup, the data may be unrecoverable.
5. **Prevention:** Versioning, Object Lock or MFA Delete for critical data, restrict `s3:DeleteObject`/`DeleteObjectVersion`, review lifecycle rules, require `--dryrun` for sync deletes, replicate to a protected account.
6. **Interview explanation:** "Versioning turns a delete into a delete marker, so I removed the marker and the object returned. Then I found the cause in CloudTrail and tightened the process."

#### A3. Static website returns 403

1. **Problem:** The CloudFront site shows `AccessDenied`/403.
2. **Possible causes:** Bucket policy lacks the CloudFront OAC statement or wrong distribution ARN, object missing (S3 returns 403 for missing objects when the caller lacks `ListBucket`), SSE-KMS key policy does not allow CloudFront, Block Public Access with a public-policy approach, wrong origin type.
3. **Procedure:** Confirm the object exists, review the bucket policy, confirm the origin uses OAC with the REST endpoint, check KMS (OAC with SSE-KMS needs the key policy to allow CloudFront).
4. **Resolution:** Correct the policy or distribution ARN. Grant `s3:ListBucket` if you want 404 instead of 403 for missing keys.
5. **Prevention:** Terraform module for site + OAC + policy, smoke test after deploy.

### Intermediate scenarios

#### B1. EC2 or EKS pod in a private subnet cannot reach S3

1. **Problem:** `aws s3 ls` hangs or times out from a private subnet.
2. **Symptoms and impact:** Timeouts (network) versus `AccessDenied` (authorization). A timeout means the **path** is broken.
3. **Possible causes:** No NAT route and no S3 gateway endpoint, endpoint not associated with the **subnet's route table**, endpoint policy blocking, security group/NACL egress, DNS issue, wrong Region endpoint.
4. **Procedure:**
   1. `aws sts get-caller-identity` (credentials work?).
   2. `curl -v https://s3.<region>.amazonaws.com` for a quick connectivity test.
   3. Check the route table for the S3 **prefix list route to the endpoint**.
   4. Check the endpoint policy and the bucket policy conditions (`aws:SourceVpce`).
   5. Check the IAM role (instance profile or IRSA) separately.
5. **Root cause (typical):** The gateway endpoint existed but was not associated with the private route table.
6. **Resolution:** Associate the endpoint with the correct route tables.
7. **Prevention:** Standard VPC module that always attaches the S3 endpoint; test from each subnet in CI.
8. **Interview explanation:** "Timeout meant network, not IAM. I traced the route table and found the endpoint missing from that subnet's table."

#### B2. Replication is not working

1. **Problem:** Objects are not appearing in the destination bucket.
2. **Possible causes:** Versioning not enabled on one side, rule filter does not match, objects created **before** the rule, replication role lacks permissions, destination bucket policy blocks the role, **KMS** permissions or encryption option missing, ownership/ACL issues, delete or lifecycle expectations misunderstood.
3. **Procedure:**
   1. `get-bucket-replication` on the source. Check the rule status, filter and role ARN.
   2. `head-object` on a source object. Look at `ReplicationStatus` (`PENDING`, `FAILED`, `COMPLETED`).
   3. Check versioning on both buckets.
   4. Check the role policy and the destination bucket policy.
   5. For KMS objects: confirm KMS replication is enabled in the rule and the role has `kms:Decrypt` on the source key and `kms:Encrypt` on the destination key.
   6. Enable replication metrics/events to see failure reasons.
4. **Resolution:** Fix the missing piece. Use **Batch Replication** to retry failed and copy existing objects.
5. **Prevention:** Replication defined in Terraform, alarms on `OperationsFailedReplication`, periodic test objects.
6. **Interview explanation:** "I checked the replication status on a sample object, then verified versioning, the role, bucket policy and KMS in that order."

#### B3. Uploads of large files are slow or fail

1. **Problem:** A 20 GB backup upload takes hours or fails near the end.
2. **Possible causes:** Single-threaded or single `PUT` upload, low bandwidth, high latency to the Region, small part size with many requests, timeouts and no retry, saturated NAT or proxy, CPU limits on checksum.
3. **Procedure:** Measure throughput (`iperf`/transfer test), check the CLI multipart settings, check for `RequestTimeout`/`SlowDown`, check the network path (NAT, proxy, VPN), try from an in-Region host.
4. **Resolution:** Use multipart with larger part sizes and more concurrency, use Transfer Acceleration for distant clients, upload from in-Region compute, use an S3 gateway endpoint to bypass NAT limits.
5. **Prevention:** Standard upload tooling with tuned settings, lifecycle rule for incomplete uploads, checksums for integrity.

#### B4. Unexpected S3 bill increase

1. **Problem:** The S3 bill rose sharply.
2. **Possible causes:** Noncurrent versions piling up, incomplete multipart uploads, log or backup growth, lots of small-object requests, data transfer out (public downloads or a crawler), replication, KMS requests, Glacier retrievals, CloudTrail data events.
3. **Procedure:** Follow section 14.3.
4. **Root cause (typical):** A versioned logging bucket without any noncurrent-version expiry, plus abandoned multipart uploads.
5. **Resolution:** Add lifecycle rules for noncurrent versions and multipart cleanup, compress logs, move older data to a cheaper class.
6. **Prevention:** Storage Lens dashboards, budgets and anomaly detection, lifecycle in the default Terraform module.
7. **Interview explanation:** "I broke the spike down by usage type, found noncurrent versions and multipart parts, then fixed it with lifecycle rules and added alerts."

### Advanced scenarios

#### C1. Bucket found publicly accessible

1. **Problem:** A scanner or Access Analyzer reports a public bucket.
2. **Impact:** Possible data exposure, compliance incident.
3. **Procedure (contain, then investigate):**
   1. **Contain:** enable **Block Public Access** on the bucket and account immediately. Remove public policy/ACL statements.
   2. **Assess:** was data actually accessed? Review **CloudTrail data events**, **server access logs**, and CloudFront logs if applicable. Use Access Analyzer and Macie to see what sensitive data was exposed.
   3. **Find the cause:** who changed the policy (CloudTrail `PutBucketPolicy`), which pipeline or person, and why.
   4. **Follow the incident process:** notify security, legal and compliance if sensitive data was exposed. Rotate any exposed credentials or secrets found in the data.
4. **Prevention:** Account-level BPA, SCP denying `s3:PutAccountPublicAccessBlock` changes, Config rules and auto-remediation, Terraform review, Access Analyzer alerts.
5. **Interview explanation:** "Contain first, then work out whether any data was actually read, using logs, and then fix the control that allowed it."

#### C2. SSE-KMS throttling and high KMS cost

1. **Problem:** A high-throughput workload sees `ThrottlingException`/slowdowns and a large KMS bill.
2. **Cause:** Every object operation calls KMS, and KMS has per-account request quotas.
3. **Procedure:** Check CloudWatch KMS metrics and CloudTrail for the key, and count requests per second.
4. **Resolution:** Enable **S3 Bucket Keys**, spread across prefixes, use exponential backoff, request a quota increase if needed, or use SSE-S3 for data that does not need key-level control.
5. **Prevention:** Capacity-plan KMS use, test at expected load.

#### C3. Cross-account access fails

1. **Problem:** A role in Account A cannot read a bucket in Account B.
2. **Causes:** Bucket policy in B does not allow Account A principal, Account A's identity policy lacks the permission, SCP blocks, **KMS key policy** in B does not allow Account A, objects owned by a different account with ACLs enabled, VPC endpoint policy.
3. **Procedure:** Both sides must allow. Check identity policy (A), bucket policy (B), KMS key policy, SCPs, endpoint policy and object ownership.
4. **Resolution:** Fix the missing statement. Prefer **bucket owner enforced** to avoid ownership problems. An alternative is for A to **assume a role in B**.
5. **Prevention:** Standard cross-account patterns in modules, Access Analyzer review.

#### C4. Ransomware or malicious deletion protection

1. **Problem:** A compromised credential tries to delete or encrypt backups.
2. **Defences:** Versioning, **Object Lock (compliance mode)** on backup buckets, **cross-account replication** to a locked-down account where the replication role cannot delete, strict IAM (deny `DeleteObjectVersion` for most roles), MFA Delete, alerts on delete spikes, short-lived credentials.
3. **Recovery:** Restore from previous versions or the replica, rotate credentials, investigate with CloudTrail.
4. **Interview explanation:** "I'd use layers: immutability with Object Lock, a separate account copy, and least privilege, then test restores regularly."

## 17. Security, Reliability and Best Practices

### 17.1 Mandatory controls vs optional design choices

| Area | **Mandatory** | Optional (depends on need and cost) |
| --- | --- | --- |
| Public access | Block Public Access ON (account and bucket) unless a bucket is deliberately public | Public buckets for specific open datasets (with review) |
| Access control | Least-privilege IAM and bucket policies, no ACL reliance (bucket owner enforced) | Access points, S3 Access Grants |
| Credentials | Roles or short-lived credentials, no static keys in CI | Per-job scoped roles |
| Encryption in transit | Deny non-TLS requests | Minimum TLS version condition |
| Encryption at rest | Default encryption on (SSE-S3 at minimum) | SSE-KMS with customer-managed keys and Bucket Keys, DSSE-KMS |
| Recovery | Versioning on important buckets, tested restore | MFA Delete, cross-Region copies |
| Immutability | None universally mandatory | **Object Lock** for regulated or ransomware-sensitive data |
| Audit | CloudTrail management events, CloudTrail data events for sensitive buckets | Server access logs, Macie, Storage Lens advanced |
| Lifecycle | Noncurrent-version and multipart cleanup rules | Tiering to IA/Glacier, Intelligent-Tiering |
| Network | S3 gateway endpoint for private workloads | Endpoint policies, interface endpoints, data-perimeter policies |
| IaC | Buckets defined in code with review | Policy-as-code (OPA, Checkov, Config) |

### 17.2 Least privilege and secrets

1. Grant specific actions on specific prefixes. Split read, write and admin roles.
2. Do not store credentials in code or Jenkins configuration. Use roles, OIDC federation (for GitHub Actions and similar), IRSA or Pod Identity for EKS.
3. Do not put secrets in S3 objects without encryption and strict access. Use Secrets Manager for secrets.
4. Use **IAM Access Analyzer** to review external access and unused permissions.

### 17.3 Network and access controls

1. Use S3 **gateway endpoints** for private workloads and **endpoint policies** to limit which buckets can be reached.
2. Use bucket policy conditions (`aws:SourceVpce`, `aws:PrincipalOrgID`) for a data perimeter, with break-glass exceptions tested.
3. Restrict who can change bucket policies and Block Public Access settings (SCPs and IAM).
4. Use CloudFront with OAC instead of public buckets.

### 17.4 High availability and disaster recovery

1. S3 is designed for high durability across AZs (except One Zone classes). Regional failure needs **CRR** or another Region copy.
2. Replicate critical data to a **separate account and Region** with restricted deletion.
3. Know your **RPO/RTO** for restore. Archive classes and large datasets take time to restore.
4. Test restore procedures (versions, replicas, Glacier restore time).
5. Consider **Multi-Region Access Points** for multi-Region read/write routing (verify current features).

### 17.4.1 Rollback and failure recovery

1. Use **versioned artifact paths** so a rollback just deploys a previous key.
2. Keep Terraform state buckets versioned so a bad state can be rolled back.
3. Keep lifecycle rules changes under review, since they can delete data silently.

### 17.5 Monitoring, logging and alerting

See section 13.3. Add alerts for policy changes, public exposure, replication failures, 5xx spikes and cost anomalies.

### 17.6 Scalability and performance

1. S3 scales automatically. Design prefixes for request-rate needs.
2. Parallel multipart and range GETs for large objects.
3. CloudFront for read-heavy content.
4. Backoff and retries (SDK defaults) for 503 errors.

### 17.7 Cost optimisation

See section 14.2.

### 17.8 Backup and recovery

1. S3 is often the **backup target** for other systems, so protect it as the last line of defence (Object Lock, separate account, restricted deletes).
2. **AWS Backup** can back up S3 with versioning (verify current features).
3. Test restoring individual objects and whole prefixes.

### 17.9 Compliance considerations

1. Regulations (PCI DSS, HIPAA, financial retention rules) usually require encryption, access logging, retention and immutability. Use Object Lock, CloudTrail data events, KMS and Macie as evidence.
2. Data residency: pick the Region carefully and block replication to disallowed Regions.
3. These notes are not compliance advice. Verify your standard's requirements.

## 19. Enterprise Reference Architecture

### 19.1 Multi-account S3 data and artifact platform

```text
AWS Organization
 |
 +-- Log archive account
 |     +-- S3: CloudTrail, Config, ALB and VPC Flow Logs (Object Lock + lifecycle, write-only for producers)
 |
 +-- Backup (vault) account
 |     +-- S3: replica buckets (CRR/SRR destination), Object Lock compliance mode, no delete for workload roles
 |
 +-- Shared-services account
 |     +-- S3: artifact buckets (Jenkins/CI upload, deploy roles read-only), Terraform state buckets
 |
 +-- Workload accounts (prod / non-prod)
       +-- S3: application data, static site buckets (private, behind CloudFront + OAC)
       +-- S3 gateway endpoint in each VPC, endpoint policy limited to approved buckets
       +-- KMS keys per environment/data class
```

### 19.2 Control flow

1. SCPs: deny disabling Block Public Access, deny `s3:DeleteBucket` outside the platform role, deny actions outside approved Regions.
2. Terraform modules create buckets with the secure baseline (BPA, versioning, encryption, TLS-only, lifecycle hygiene, tags, logging).
3. CI/CD uses OIDC or instance roles, with separate upload and deploy roles.
4. Config rules, Security Hub and Access Analyzer detect drift and exposure.
5. Replication copies critical buckets into the backup account with Object Lock.
6. Storage Lens and Cost Explorer dashboards track cost and usage by tag.

### 19.3 Design decisions to explain

1. **Why a separate backup account?** A compromised workload account cannot delete the backups.
2. **Why versioned artifact paths?** Reproducible deployments, instant rollback.
3. **Why gateway endpoints?** Private access and lower NAT cost.
4. **Why SSE-KMS only for some buckets?** Key-level control and audit where required, SSE-S3 elsewhere to save cost and avoid KMS quota issues.
5. **Why CloudFront + OAC?** Private bucket, HTTPS, caching and WAF.

## 20. Interview Questions and Answers

> Answer pattern: **definition → how it works → trade-off or example → follow-up**. Follow-up questions a senior interviewer may ask are shown as **Follow-up**.

### 20.1 Basic concepts

#### Q1. What is Amazon S3 and when do you use it?

1. S3 (Simple Storage Service) is AWS object storage. Data is stored as objects in buckets and accessed over an HTTPS API.
2. It is designed for 11-nines durability, virtually unlimited scale and pay-as-you-go pricing.
3. Use it for artifacts, backups, logs, static assets, data lakes and Terraform state.
4. Do not use it as a POSIX file system, a low-latency database or a block device.
5. **Follow-up:** "What would you use instead for a shared file system?" EFS (or FSx). For a server disk, EBS.

#### Q2. What is the difference between a bucket, an object and an object key?

1. **Bucket:** top-level container, in one Region, with a globally unique name.
2. **Object:** the data plus metadata, identified by a key (and a version ID if versioning is on).
3. **Key:** the full name of the object in the bucket, such as `releases/1.2.0/app.jar`. The `releases/1.2.0/` part is a **prefix**.
4. The slash is only a character. The Console displays folders for convenience.

#### Q3. Is S3 a file system?

1. No. S3 is a flat object store with keys and metadata.
2. No in-place edits, no append, no file locking, no real directories, and renaming means copy plus delete.
3. Tools like **Mountpoint for Amazon S3** or s3fs can present a file-like view, but with limits on supported operations and with performance trade-offs.
4. **Follow-up:** "Why does `aws s3 mv` of a big prefix take so long?" Each object is copied then deleted.

#### Q4. What are S3 storage classes and how do you choose one?

1. Classes trade **storage cost** against **retrieval cost, speed and availability**: Standard, Intelligent-Tiering, Standard-IA, One Zone-IA, Glacier Instant/Flexible/Deep Archive (and Express One Zone for low latency).
2. Choose by access pattern: frequent = Standard, unknown = Intelligent-Tiering, infrequent = IA, archive = Glacier classes, recreatable and non-critical = One Zone-IA.
3. Mind **minimum storage durations**, **minimum object size** and **retrieval fees**.
4. Archive classes may need a **restore** before reading.
5. **Follow-up:** "How do objects move between classes?" Lifecycle rules, or set at upload, or Intelligent-Tiering automatically.

#### Q5. What consistency model does S3 provide?

1. **Strong read-after-write consistency** for new objects, overwrites, deletes and list operations (since December 2020), in all Regions, at no extra cost.
2. After a successful write, a read or list reflects it.
3. Concurrent writes to the same key: last writer wins, with no object locking. Use versioning or application-level coordination if needed.
4. **Follow-up:** "Does this make S3 a good place for a lock file?" Not by itself. Use DynamoDB or S3 conditional writes (verify current support) for coordination.

#### Q6. What is the difference between durability and availability in S3?

1. **Durability** (11 nines design) is about **not losing** data. **Availability** is about being able to **access** it right now, and it varies by storage class.
2. Durability comes from redundant storage across devices and (for most classes) at least three AZs.
3. Durability does **not** protect from your own deletes, bad lifecycle rules or credential compromise. Use versioning, Object Lock, replication and least privilege.

#### Q7. What are the object size limits and how do you upload large files?

1. Maximum object size: **5 TB**.
2. Maximum for a single `PUT`: **5 GB**. Larger objects **must** use **multipart upload**. Use multipart above roughly 100 MB for performance.
3. Multipart: parts of 5 MiB to 5 GiB (the last can be smaller), up to 10,000 parts.
4. Verify limits in the current documentation before quoting them in a design.

### 20.2 Intermediate concepts

#### Q8. What is S3 versioning, and what is a delete marker?

1. Versioning keeps every version of an object under the same key, each with a version ID.
2. Deleting without a version ID adds a **delete marker**. The object looks deleted, but versions remain.
3. Removing the delete marker restores the latest version. Deleting a specific version ID is permanent.
4. Once enabled, versioning can only be **suspended**, not removed.
5. It requires lifecycle rules for noncurrent versions, or cost grows without limit.
6. It is needed for replication and Object Lock.

#### Q9. What is an S3 lifecycle policy and what are the risks?

1. It automatically **transitions** objects between classes or **expires** them by age, filtered by prefix, tag or size.
2. It can also expire noncurrent versions, remove expired delete markers and abort incomplete multipart uploads.
3. Risks: deleting data permanently with a wrong prefix or empty filter, transitioning small objects (cost), minimum-duration charges, and asynchronous execution (not instant).
4. Test on a non-production prefix and review retention requirements.
5. In a versioned bucket, current-version expiration only **adds a delete marker**. Noncurrent expiration removes versions.

#### Q10. IAM policy vs bucket policy: when do you use each?

1. IAM policy is attached to an identity and defines what that identity can do. A bucket policy is attached to a bucket (needs `Principal`) and defines who can access it.
2. Same account: either can allow, but any explicit deny wins.
3. Cross-account: **both** sides must allow.
4. Use bucket policies for cross-account access, TLS and encryption enforcement and network conditions. Use IAM policies for per-role permissions.
5. Watch the ARN split: `ListBucket` on the bucket ARN, `GetObject`/`PutObject` on `bucket/*`.

#### Q11. What is Block Public Access, and what about ACLs?

1. BPA is an account- and bucket-level guardrail that blocks public ACLs and public policies, even if someone tries to add them.
2. It has four settings (`BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, `RestrictPublicBuckets`). Enable all four unless a bucket is deliberately public.
3. ACLs are legacy. New buckets use **Bucket owner enforced** (ACLs disabled), and the owner owns all objects.
4. **Follow-up:** "Why do cross-account uploads sometimes cause 'cannot read object' errors?" Object ownership with ACLs enabled. Bucket owner enforced removes the problem.

#### Q12. SSE-S3 vs SSE-KMS?

1. SSE-S3: S3-managed keys, no extra cost, default. SSE-KMS: keys in KMS with key policies, audit in CloudTrail and rotation control, but KMS request cost and quotas.
2. SSE-KMS needs `kms:Decrypt` or `kms:GenerateDataKey` for the caller, and the key policy must allow it (including cross-account).
3. Use **S3 Bucket Keys** to reduce KMS calls.
4. Choose SSE-KMS for regulated data or when you need key-level control and audit.

#### Q13. What is a presigned URL, and what are its risks?

1. A URL that grants temporary access to one object (GET or PUT) using the creator's permissions.
2. Max expiry is 7 days with IAM user credentials. With role credentials it ends when the session expires.
3. Anyone with the URL can use it until expiry, so keep it short and do not log it.
4. If the creator's permissions are revoked, the URL stops working.
5. Use cases: browser uploads, temporary report sharing.

#### Q14. How does multipart upload work, and what is the hidden cost?

1. Initiate (get an upload ID), upload parts in parallel, then complete with the part list.
2. Benefits: speed, retry of individual parts, pause and resume.
3. Hidden cost: incomplete uploads keep their parts, billed as storage. Add `AbortIncompleteMultipartUpload` to lifecycle (for example 7 days). Find them with `list-multipart-uploads`.

#### Q15. SRR vs CRR: what are the differences and prerequisites?

1. Both replicate new objects asynchronously. SRR stays in-Region, CRR crosses Regions.
2. Prerequisites: versioning on both buckets, an IAM role for S3, a rule with filter, and KMS permissions if encrypted.
3. Use SRR for log aggregation, separate copies or account isolation. Use CRR for DR, latency and geographic compliance.
4. Existing objects need **Batch Replication**. Replication is not chained.
5. RTC provides an SLA-backed time target at extra cost.

#### Q16. How do you host a static website with S3 securely?

1. Keep the bucket **private** with Block Public Access on.
2. Put **CloudFront** in front with **Origin Access Control** and a bucket policy allowing only the distribution.
3. Add HTTPS with an ACM certificate (in `us-east-1` for CloudFront), WAF if needed, caching and a Route 53 alias.
4. The S3 website endpoint alone is HTTP-only and needs a public bucket, so avoid it for production.
5. Handle SPA routing with CloudFront custom error responses and invalidate caches on deployments.

#### Q17. How can EC2 or EKS workloads access S3 securely from private subnets?

1. Identity: an **IAM role** (instance profile, or IRSA/Pod Identity for pods) with least-privilege S3 permissions.
2. Network: an **S3 gateway endpoint** associated with the private route tables (no NAT needed, no endpoint charge). Add an endpoint policy to limit buckets.
3. Bucket side: bucket policy conditions such as `aws:SourceVpce` or `aws:PrincipalOrgID` if you want a data perimeter.
4. Troubleshoot timeouts (network) separately from `AccessDenied` (authorization).

#### Q18. How do you monitor and audit S3?

1. CloudWatch storage metrics and optional request metrics (errors, latency, bytes).
2. CloudTrail management events for bucket changes and **data events** for object access (not on by default, charged).
3. Server access logs for cheap, delayed request logs.
4. Config rules for public or unencrypted buckets, Access Analyzer for external access, Macie for sensitive data, GuardDuty for threats.
5. Storage Lens and Cost Explorer for usage and cost.
6. Alerts on policy changes, BPA changes, replication failures, 5xx spikes and cost anomalies.

### 20.3 Advanced technical questions

#### Q19. What is S3 Object Lock?

1. WORM (Write Once, Read Many) protection of object **versions**, requiring versioning.
2. **Governance mode:** users with special permission can bypass. **Compliance mode:** nobody, including root, can delete or shorten retention until it expires. **Legal hold:** indefinite lock until removed.
3. Use for regulatory retention and ransomware-resistant backups.
4. Test with Governance mode first, because Compliance mode is irreversible for the retention period.

#### Q20. How do you set up cross-account access to a bucket?

1. Option 1: **bucket policy** in the owning account naming the other account's role, plus an **identity policy** in the caller's account allowing the actions.
2. Option 2: the caller **assumes a role** in the bucket owner's account, which has direct permissions.
3. If SSE-KMS is used, the **KMS key policy** must allow the caller too.
4. Prefer Bucket owner enforced to avoid ownership problems. Review external access with Access Analyzer.
5. Use `aws:PrincipalOrgID` to allow the whole Organization instead of listing accounts.

#### Q21. How do you enforce TLS and encryption for a bucket?

1. TLS: a bucket policy with `Deny` when `aws:SecureTransport` is `false`.
2. Encryption: set **default encryption** (SSE-S3 or SSE-KMS). Optionally deny `PutObject` without the required encryption header, but test client and replication behaviour first.
3. For minimum TLS version use the `s3:TlsVersion` condition (verify support).
4. Enforce through Terraform modules and Config rules, and alert on drift.

#### Q22. Why can SSE-KMS cause throttling or high cost, and what do you do?

1. Each object operation can call KMS, and KMS has per-account request quotas and per-request charges.
2. Fix with **S3 Bucket Keys**, backoff and retries, spreading load, a quota increase if justified, or SSE-S3 for data that does not need KMS-level control.
3. Remember that CloudTrail KMS events change with Bucket Keys (bucket-level key).

#### Q23. How do you get high S3 performance?

1. Parallelise: multipart uploads and **byte-range GETs**.
2. Spread request load across **prefixes** (limits are per prefix: at least 3,500 writes and 5,500 reads per second).
3. Retry with exponential backoff on `503 Slow Down`.
4. Co-locate compute in the same Region, use CloudFront for reads and Transfer Acceleration for distant uploads.
5. Batch tiny files. Consider Express One Zone for very low-latency needs.

#### Q24. How would you build an event-driven pipeline on S3 uploads?

1. Configure S3 Event Notifications (or EventBridge) for `ObjectCreated` on a prefix and suffix.
2. Send to **SQS** (buffering, retries, DLQ) and have workers or Lambda process.
3. Make consumers **idempotent** because delivery is at least once.
4. Write outputs to a **different prefix or bucket** to avoid trigger loops.
5. Add monitoring for queue depth, DLQ and error rates.

#### Q25. What are the caveats of S3 replication?

1. Only new objects replicate (use Batch Replication for existing ones).
2. Versioning is required on both buckets.
3. Replicas are not re-replicated (no chaining by default).
4. Version-specific deletes are not replicated. Delete markers are optional.
5. Lifecycle actions are not replicated.
6. KMS-encrypted objects need explicit support and permissions.
7. Replication copies bad writes too. It is not a backup by itself.

#### Q26. What are S3 Access Points and why use them?

1. Named network endpoints attached to a bucket, each with its own policy and optionally a VPC restriction.
2. They make it easier to manage access for many applications or teams on a shared bucket without one huge bucket policy.
3. **Multi-Region Access Points** provide a global endpoint that routes to replicated buckets (verify current feature details).

### 20.4 Scenario-based and production troubleshooting questions

#### Q27. A pipeline gets `AccessDenied` on `PutObject`. How do you troubleshoot?

1. `aws sts get-caller-identity`: verify account and role.
2. Confirm bucket, key and Region.
3. Check the identity policy (object ARN `bucket/prefix/*`).
4. Check the bucket policy for explicit denies (TLS, encryption header, source VPC, principal conditions).
5. Check KMS permissions and key policy if SSE-KMS.
6. Check SCPs, permission boundaries and endpoint policies.
7. Use the policy simulator and CloudTrail to find the denying layer. Fix with the minimum permission.

#### Q28. EC2 in a private subnet cannot reach S3. What do you check?

1. Timeout or `AccessDenied`? Timeout means network. `AccessDenied` means authorization.
2. Credentials via `get-caller-identity` and the instance role.
3. S3 gateway endpoint exists **and** is associated with the subnet's route table.
4. Endpoint policy and bucket policy (`aws:SourceVpce`) conditions.
5. Security group egress, NACLs, DNS and the right Region.

#### Q29. An important object was deleted. How do you recover it?

1. Check whether versioning is on.
2. `list-object-versions` for the key: look for a delete marker or older versions.
3. Delete the **delete marker** (by its version ID), or copy an older version back as current.
4. Use CloudTrail data events and lifecycle configuration to find who or what deleted it.
5. If versioning was off and there is no replica or backup, recovery may be impossible. Prevent this with versioning, Object Lock, restricted delete permissions and replication.

#### Q30. A bucket is publicly accessible. What do you do?

1. **Contain:** enable Block Public Access (bucket and account), remove public policy/ACL statements.
2. **Assess:** use CloudTrail data events, server access logs, CloudFront logs, Access Analyzer and Macie to see whether data was read and what it contained.
3. **Cause:** find the `PutBucketPolicy`/ACL change in CloudTrail and who made it.
4. Follow the incident process (security, legal, compliance), rotate any exposed secrets.
5. **Prevent:** account-level BPA, SCP protecting BPA settings, Config rules with remediation, reviewed Terraform.

#### Q31. Uploads of large files are slow. What do you do?

1. Measure throughput and request times, and look for `RequestTimeout` or `503`.
2. Use multipart with larger parts and more concurrency.
3. Upload from compute in the same Region, avoid NAT bottlenecks with a gateway endpoint.
4. Use Transfer Acceleration for distant clients (extra cost).
5. Verify integrity with checksums, and clean up failed uploads with lifecycle rules.

#### Q32. Replication is not working. What do you check?

1. Versioning on both buckets.
2. The rule is enabled, with the right filter, destination and role.
3. The object was created **after** the rule (otherwise use Batch Replication).
4. `ReplicationStatus` on a sample object (`PENDING`, `FAILED`, `COMPLETED`).
5. Role permissions, destination bucket policy and KMS permissions (and KMS replication enabled in the rule).
6. Replication metrics and events for failure reasons.

#### Q33. Your S3 bill increased significantly. How do you investigate and reduce it?

1. Cost Explorer by usage type, bucket tag and Region. Compare with the previous month.
2. Check storage growth by class, noncurrent versions, incomplete multipart uploads, request counts, data transfer out, replication, KMS and CloudTrail data events.
3. Fix: lifecycle rules (noncurrent expiry, multipart abort, tiering), Intelligent-Tiering where suitable, compress and compact small objects, CloudFront for repeat downloads, gateway endpoints to cut NAT cost, Bucket Keys.
4. Add budgets, anomaly detection and Storage Lens dashboards. Track the next bill.

#### Q34. How do you design an S3 bucket for Terraform remote state?

1. Dedicated bucket per environment or account, **versioning on**, **encryption on**, **Block Public Access on**, TLS-only policy.
2. State locking: S3-native locking in recent Terraform versions (verify) or DynamoDB for older versions.
3. Access only for the Terraform execution role and a break-glass role. State can contain secrets.
4. Lifecycle for noncurrent versions (keep enough history for rollback), optional replication to another account.
5. Alerts on changes to the bucket policy and deletion attempts.

#### Q35. How should Jenkins authenticate to S3?

1. Use an **IAM role** (instance profile, IRSA or Pod Identity for agents on EKS) or an assumed role, not static access keys in Jenkins credentials.
2. Use a **separate upload role** (`s3:PutObject` on `releases/*`) and a **deploy role** (`s3:GetObject`).
3. Do not expose cloud credentials to untrusted pull-request builds. Restrict upload stages to protected branches.
4. Use versioned artifact paths and checksums, and fail fast with `aws sts get-caller-identity`.

### 20.5 Security and best-practice questions

#### Q36. How do you secure a new S3 bucket?

1. Block Public Access on, ACLs disabled (Bucket owner enforced).
2. Least-privilege IAM and bucket policy, no wildcard principals without strong conditions.
3. TLS-only policy, default encryption (SSE-S3 or SSE-KMS with Bucket Keys).
4. Versioning, lifecycle hygiene (noncurrent versions, multipart cleanup) and optional Object Lock.
5. Logging: CloudTrail (data events for sensitive buckets), optional server access logs.
6. Private access through gateway endpoints for VPC workloads.
7. Tags, Config rules, Access Analyzer, Macie for sensitive data, and replication to a protected account for critical data.
8. Everything in Terraform with review.

#### Q37. How do you prevent data exfiltration from S3 (a data perimeter)?

1. **Identity perimeter:** only principals from your organisation (`aws:PrincipalOrgID`) can access the buckets.
2. **Network perimeter:** only from your VPC endpoints or IP ranges (`aws:SourceVpce`, `aws:SourceVpc`), with endpoint policies restricting which buckets can be reached from your VPCs.
3. **Resource perimeter:** SCPs and endpoint policies limit access to resources owned by your Organization (`aws:ResourceOrgID`).
4. Exceptions for AWS service principals, CI and break-glass must be designed and tested to avoid lockouts.
5. Add monitoring: Access Analyzer, GuardDuty and alerts on policy changes.

### 20.6 Follow-up questions a senior interviewer may ask

1. "How do you migrate 200 TB into S3?" Assess bandwidth. Use DataSync over Direct Connect/VPN, or Snowball for offline transfer. Verify integrity with checksums, run in parallel, cut over by prefix, and set lifecycle rules afterwards.
2. "Why not give developers `s3:*` on `*` in dev?" Dev mistakes still delete data or leak keys, and habits carry to prod. Use scoped permissions and sandbox accounts.
3. "How would you rotate a KMS key used by S3?" Enable automatic rotation for customer-managed keys. The key ID stays the same and old data remains decryptable. Re-encrypting objects under a new key needs a copy operation (Batch Operations).
4. "A lifecycle rule deleted production releases. What changes?" Scope rules by prefix, add change review and a dry-run process (Inventory first), enable versioning and Object Lock where needed, and alert on lifecycle changes.
5. "How do you share a 5 GB report with an external partner?" A presigned URL with short expiry, or a role in your account (or their account) with scoped access. Avoid public buckets.
6. "S3 returns 403 for a missing object but 404 for others. Why?" Without `s3:ListBucket`, S3 returns 403 for missing keys to avoid revealing existence. With it, you get 404.
7. "How would you make S3 reads cheaper at scale?" CloudFront caching, larger objects with range reads, compression and keeping consumers in-Region.

## 21. Interview Answer Framework

Use this for any scenario question. Say the steps aloud.

### 21.1 The eight-step framework

| Step | What you say | S3-specific examples |
| --- | --- | --- |
| 1. Understand problem and impact | What fails, for whom, since when, what changed? | Upload failing for CI? Public exposure? Cost spike? |
| 2. Check monitoring, logs, metrics, events | Evidence before changes | CloudTrail, S3 request metrics, Storage Lens, replication metrics |
| 3. Verify architecture and configuration | Bucket, Region, policies, endpoint, KMS, versioning | `get-bucket-policy`, `get-public-access-block`, route table, key policy |
| 4. Narrow down root causes | Rank hypotheses | Identity vs bucket policy vs KMS vs network vs lifecycle |
| 5. Run safe diagnostics | Read-only commands | `sts get-caller-identity`, `head-object`, `list-object-versions`, policy simulator |
| 6. Apply the safest fix and validate | Smallest change, with rollback | One policy statement, endpoint association, restore a version |
| 7. Communicate and document | Status, timeline, root cause | Incident note, owner, follow-ups |
| 8. Prevent recurrence | Monitoring or automation | Config rule, SCP, Terraform module, lifecycle hygiene, alarms |

### 21.2 S3-specific adaptations

1. **Permission problems:** identity -> identity policy -> bucket policy (explicit deny) -> KMS key policy -> SCP/boundary -> endpoint policy -> Block Public Access.
2. **Network problems:** timeout vs AccessDenied -> route table and gateway endpoint -> endpoint policy -> DNS/Region -> SG/NACL.
3. **Data loss problems:** versioning -> delete markers -> lifecycle and CloudTrail -> replicas and backups.
4. **Cost problems:** usage type -> bucket -> storage class and versions -> requests and transfer -> multipart and replication.
5. **Security incidents:** contain first, then assess with logs, then fix the control.

### 21.3 Worked example (about 90 seconds)

> **Question:** "Your Jenkins pipeline suddenly fails to upload artifacts to S3 with AccessDenied. What do you do?"
>
> "First I'd check the impact: which jobs and branches fail, since when, and what changed recently, such as a role, policy, bucket or Jenkins agent change. Then I'd look for evidence in CloudTrail for the failed `PutObject` and any recent `PutBucketPolicy` or IAM changes.
>
> I'd verify what identity the agent is using with `aws sts get-caller-identity`. My hypotheses would be a wrong role or expired credentials, a changed bucket policy with an explicit deny, a missing KMS permission, or an SCP change. I'd run read-only checks: the identity policy for the object ARN, the bucket policy, the KMS key policy and the policy simulator.
>
> If, for example, the bucket policy now requires an encryption header or the role lost `kms:GenerateDataKey`, I'd apply the smallest fix through Terraform with review, rerun the pipeline to validate, and note the root cause. For prevention I'd add a policy-simulation check in CI, alerts on bucket policy changes, and keep upload and deploy roles scoped separately."

### 21.4 Delivery tips

1. State assumptions ("assuming SSE-KMS and a gateway endpoint").
2. Prefer read-only diagnostics first and say so.
3. Mention trade-offs (cost versus durability, SSE-S3 versus SSE-KMS).
4. Do not claim you built something you did not. Use "in a design like this I would…" for hypotheticals, and use your real project experience only where it is genuinely yours.

## 22. Quick Revision

### 22.1 Key points to remember

1. S3 = object storage. Buckets are regional with globally unique names. Keys with `/` are not real folders.
2. Max object **5 TB**. Single PUT max **5 GB**. Use multipart above ~100 MB.
3. **Strong** read-after-write consistency. Durability 11 nines (not protection from your own mistakes).
4. Delete in a versioned bucket = **delete marker**. Remove the marker to restore.
5. Lifecycle can delete data permanently. Scope prefixes carefully. Add noncurrent-version and multipart cleanup.
6. Block Public Access on. ACLs off (bucket owner enforced). Policies decide access. Explicit deny wins.
7. Cross-account needs **both sides** (and KMS if used).
8. SSE-S3 by default. SSE-KMS for key control and audit (watch permissions, cost, throttling). Bucket Keys help.
9. Replication needs versioning on both sides, only new objects, no chaining, not a backup by itself.
10. Static sites: private bucket + CloudFront + OAC.
11. Private workloads: IAM role + S3 gateway endpoint (association with the route table).
12. CloudTrail **data events** are off by default.

### 22.3 Commonly confused concepts

| Pair | Difference in one line |
| --- | --- |
| Durability vs availability | Not losing data vs being able to read it now |
| Delete marker vs permanent delete | Hidden current version vs removal of a specific version |
| Governance vs Compliance lock | Bypassable with permission vs not even root |
| IAM policy vs bucket policy | Identity-attached vs resource-attached with `Principal` |
| SSE-S3 vs SSE-KMS | AWS-managed keys vs customer-controlled KMS keys |
| SRR vs CRR | Same Region vs different Region |
| Replication vs backup | Copies new writes (including bad ones) vs recoverable history |
| Gateway vs interface endpoint | Route-based, S3/DynamoDB only vs ENI-based, reachable from on-prem |
| `s3` vs `s3api` | High-level convenience vs one-to-one API calls |
| Presigned URL vs public object | Temporary, creator's permissions vs open to everyone |
| Server access logs vs CloudTrail data events | Cheap and delayed vs near real time and charged |
| 403 vs 404 | Missing `ListBucket` hides existence behind 403 |
